## Choosing N = 3M

The keyword build is one pass in memory, so RAM sets the ceiling. Two probe builds measured peak memory footprint:

| Docs | Peak memory footprint |
| ---- | --------------------- |
| 1M   | 2.84 GB               |
| 2M   | 5.21 GB               |

That is about 2.4 GB more per million docs, which puts 3M near 7.6 GB. That fits a 16 GB laptop alongside the OS, a browser and the 1M-doc neural build that reuses the same docs. 4M would be near 10 GB, which is too close.

The probes ran while an embedding job was using the CPU, so only their memory numbers count, not their times. The 3M corpus takes the first three parquet shards (6.4 GB) plus a 9.8 GB `corpus.jsonl`.

## Build

- **Time:** 3,000,000 docs in 427 s, on one thread.
- **Memory:** peak footprint 6.93 GB (max resident 3.39 GB), under the 7.6 GB estimate.
- **Keyword index:** 926 MB (postings 795, term dictionary 94, skips 34, norms 3).
- **Doc store:** 993 MB.

## B7: exhaustive vs MaxScore over tiers

The queries are the 3,452 BEIR NQ test queries run against FineWeb docs. There are no relevance judgments for this pairing, so this is a speed test only.

- k = 10, keyword stage, single-thread latency.
- QPS is whole searches.
- 3,451 of the queries have 3 or more terms.

|                            | Exhaustive     | MaxScore            |
| -------------------------- | -------------- | ------------------- |
| Postings decoded per query | 2,729,739      | 475,726 (83% fewer) |
| p50 ms                     | 17.03          | 2.39                |
| p99 ms                     | 24.99          | 13.96               |
| QPS, 1 / 4 / 10 threads    | 60 / 165 / 196 | 315 / 1,050 / 1,799 |

- **Same results:** on every query, MaxScore's top-10 scores equal exhaustive's, rank by rank, within 1e-5 relative.
- **PRD target met:** at least 50% fewer postings decoded on 3+ term queries. It is 83% here, against 50% on TREC-COVID (171k docs). The bigger the corpus, the more the low tiers of common terms get skipped.
- **7.1x faster at p50, and p99 too:** unlike on the BEIR sets, MaxScore also wins at p99.

## B5: keyword search with domain and crawl date filters

Same queries, k = 10, MaxScore. The filters were picked to hit the target selectivities: the biggest domains, and the tightest runs of consecutive crawl days. The last column compares p50 with no filter.

| Filter                              | Selectivity | Docs allowed | Postings decoded | p50 ms | p99 ms | vs none |
| ----------------------------------- | ----------- | ------------ | ---------------- | ------ | ------ | ------- |
| none                                | 100%        | 3,000,000    | 475,726          | 2.39   | 13.73  | 1.00x   |
| the biggest domain                  | 0.13%       | 3,903        | 527,147          | 3.25   | 10.63  | 1.36x   |
| the 18 biggest domains              | 1.03%       | 30,772       | 484,798          | 3.17   | 10.09  | 1.33x   |
| crawl date 2019-09-24 to 10-13      | 0.10%       | 2,992        | 1,599,799        | 7.07   | 14.17  | 2.96x   |
| crawl date 2014-03-11 to 2015-03-26 | 1.00%       | 30,008       | 496,926          | 2.98   | 8.17   | 1.25x   |
| crawl date 2020-10-23 to 2021-01-21 | 10.0%       | 299,991      | 477,458          | 3.29   | 8.79   | 1.38x   |
| crawl date 2015-03-28 to 2019-08-21 | 50.0%       | 1,499,906    | 467,619          | 5.78   | 14.71  | 2.42x   |

- **Same results:** on every query and filter, MaxScore's filtered top 10 has the same scores as exhaustive's with the same filter. That filtered results never leave the filter is checked by the engine tests.
- **PRD target met:** latency at 1% selectivity ≤ 2x unfiltered. It is 1.33x for domains and 1.25x for crawl dates.

Two filters are slow.

**The 0.1% crawl date range decodes 3.4x the postings of no filter.**

- FineWeb's files are built from chunks of different crawl dumps, so crawl dates come in runs along doc id order (checked by sampling the corpus). Three weeks of crawl are a few contiguous blocks of doc ids.
- MaxScore can only prune once it holds k allowed hits. Until the cursors reach those blocks, every term stays essential and almost every posting before them gets decoded.
- A domain filter of the same size is spread over the whole id range, so it fills the top k early.

**The 50% range decodes fewer postings than no filter but takes 2.4x as long.** The likely cause is building the filter itself. The range is the union of the bitmaps of every crawl day in over four years, rebuilt for each query. This is not measured yet.

Not done yet, and it would help both:

- let cursors jump to the next allowed doc instead of scoring and then dropping
- cache range bitmaps or precompute them

## B8: BM25 memory, step by step

Corpus: 3,000,000 docs, 5,967,917 distinct terms, 581,804,457 postings. The rows are measured the same way as [B8 on NQ](b8-ablate-postings-2026-11-05.md).

| Format                                            | Total bytes   | Bytes per posting |
| ------------------------------------------------- | ------------- | ----------------- |
| `HashMap<String, Vec<(u32, u32)>>`                | 7,263,781,397 | 12.48             |
| + one flat buffer, (offset, len) per term         | 5,067,577,117 | 8.71              |
| + delta varint doc ids                            | 3,447,374,467 | 5.93              |
| + tf tiers (with headers and skips)               | 1,282,581,958 | 2.20              |
| + inline singletons, FST dictionary, 1-byte norms | 926,352,664   | 1.59              |

**The final format is 87% smaller than naive** (926 MB vs 7.26 GB, a ratio of 0.128), the same as on NQ (0.130). Against a varint tf (postings 1,288,847,904 bytes), the tiers cut postings bytes by 33%.
