# B12: HTTP latency per mode, with the per-stage split (7 Nov 2026)

Raw output: [`b12-http-2026-11-07.json`](b12-http-2026-11-07.json). Machine: Apple M4, 10 cores, 16 GB RAM, macOS, AC power, NEON kernel.

```bash
# DBpedia 1M: query vectors sent in the request
telusur serve --index indexes/dbpedia &
telusur bench http --queries data/dbpedia/queries.jsonl --field title --query-vectors data/dbpedia/queries.fbin

# TREC-COVID: the server embeds the query text through the sidecar
uv run --with fastembed scripts/embed_server.py &
telusur serve --index indexes/trec-covid --embedder http://127.0.0.1:8001 &
telusur bench http --queries data/trec-covid/queries.jsonl
```

**How it is measured:**

- One client sends one request at a time over HTTP/1.1 on localhost, with k = 10.
- Each mode gets a warm-up pass, then 1,000 timed requests.
- TREC-COVID has 50 queries, so each is sent 20 times.
- Request bodies are serialized before timing.
- p50 and p99 are client time, from request sent to response read.
- Stages come from the server's `timings_ms`. The table shows the p50 of each stage. The JSON also has their p99 and mean.

The indexes use their defaults (nprobe 256, rerank depth 500).

- **DBpedia:** 999,000 docs, 3072-dim OpenAI vectors, 2,048 clusters. Keyword queries use the entity title.
- **TREC-COVID:** 171,332 docs, nomic-embed-text-v1.5 on CPU in the sidecar.

No request fell back to keyword: the sidecar always answered within the 1 s timeout.

What the numbers say:

- **HTTP and JSON add about 0.1 to 0.2 ms** at p50 (client p50 minus the server's total). That includes parsing a 3072-float vector in the DBpedia neural requests.
- **The server runs neural search at in-process speed.** Route, scan and rerank take 0.57 ms here, against 0.54 ms for the same settings in the [B3 point](b4-telusur-2026-11-07.json) run the same day.
- **Hybrid costs about the same as neural on DBpedia.** The two retrievers run in parallel, and the keyword search (0.09 ms) is hidden behind the vector search. On TREC-COVID the keyword search (1.44 ms) takes longer than the vector search (0.66 ms), so hybrid adds about 0.7 ms.
- **The keyword search inside hybrid is slower than keyword mode** (0.09 vs 0.05 ms on DBpedia, 1.44 vs 0.50 on TREC-COVID). Hybrid asks each retriever for its top 100 instead of the top 10, and MaxScore skips less work at k = 100.
- **With the server embedding, embedding is over 90% of the latency** (10.7 ms p50, 17.3 ms p99). It runs in Python on CPU. The search itself takes under 1 ms.
- **In hybrid, the keyword search waits for the embedding.** The server embeds before it searches, so keyword search could overlap the embedding instead. That would save about the 0.7 ms hybrid adds over neural.

This replaces a 6 Nov run that was about twice as slow: the laptop was in Low Power Mode then. Reports now record the power state.
